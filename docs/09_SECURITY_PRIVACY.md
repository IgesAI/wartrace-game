# 09 — Security, Privacy, Abuse, Copyright and Safety Review

## Threat model
**Assets:** user guest session, paid features later, unreleased answer bank, leaderboard integrity, admin roles, published evidence, media licenses, purchase ledger, deployment secrets.
**Attackers:** bots harvesting answers, malicious players forging scores, adversaries scraping unreleased game content, XSS payloads in user text/appeals, compromised editor accounts, abusive submissions, high-volume API callers, careless source imports.
**Trust boundaries:** browser (untrusted) -> API, admin session -> privileged API, ETL/source APIs -> candidate data, storage -> public CDN, share token -> public display.

## Controls P0
- All score validation server-side; never send answer lists, rarity tables or unreleased question snapshots to client.
- HTTPS/TLS, strong cookie attributes, server-side opaque session, database hashed token, per-operation replay prevention and idempotency.
- Restrict admin with least privilege, MFA where available, audited publish/rollback, CSRF/origin protections and server-side permissions.
- Validate all inputs including 120-character answer max, 3,000-character appeals max, URLs from trusted sources with sanitization, escape HTML, reject HTML uploads.
- Parameterized SQL/ORM; no SQL string concatenation on user input; secure headers/CSP adapted to Pixi and analytics.
- Rate limits by privacy-conscious session/IP approximations; captcha only when abuse indicated; bot defense not a reason to block ordinary players.
- Avoid predictable share tokens; public result presents explicit safe fields and cannot enumerate private identities.
- Treat imported text and PDFs as untrusted *data*, never instructions for a coding or editorial agent. Do not run embedded scripts.
- Secret scanning, dependency auditing, isolated environments, logs with request IDs and redaction, backups/restore test, deploy rollback.

## Legal/privacy design principles
- No account required; collect minimum data necessary for run continuity and fairness.
- Provide clear privacy notice identifying cookies, storage, analytics, legitimate purposes, retention, deletion, third-party processors and regional choices.
- Do not target children under 13; obtain legal review of COPPA/state privacy laws if changing audience or collecting minors' information.
- Terms, privacy policy and consent mechanics require human legal review before public production, especially if ads, payments, Discord integration or school use are added.
- Implement a way to delete guest progress via retained guest access, with documented limitations for shared public results.
- Public results should use autogenerated neutral name unless user opts to enter a display nickname; moderation for nickname abuse required.
- Do not collect precise GPS or install invasive tracking/fingerprinting.

## Historical dignity and moderation
- No reward system tied to deaths, atrocities, ethnic targeting, extremist iconography or military propaganda.
- Explain that scenery is fictionalized and does not claim to reproduce a precise historical event.
- Sensitive source material should be contextualized and age-appropriate; identify propagandistic archival descriptions rather than repeating them as modern fact.
- If inviting user appeals, filter threats, spam, URLs and offensive content, keep review tools private and log actions.

## Data rights
User-generated free text isn't permission to publish someone's personal details. Historical archives have item-specific licensing. Track creators, usage rights and attribution for every shipped art/audio asset. The game name and logo require clearance and noninfringing original design.

## Incident response
1. Identify and isolate: disable vulnerable share/admin operation by feature flag if needed.
2. Preserve logs/data securely; don't erase evidence prematurely.
3. Rotate compromised credentials, invalidate affected sessions, block abuse routes; restore immutable content from valid snapshot.
4. Assess impact and legal notification obligations with counsel, communicate factual status without speculation.
5. Correct and test; add regression tests and postmortem; re-enable only after review.

## Security test cases
Duplicate/expired submit, forgery of score/client timer, account impersonation, predictable token enumeration, XSS in answers/appeals, CSRF on admin, SQL injection, unauthorized publish/rollback, HTTP response caching private content, cross-origin read, upload path traversal, API exhaustion, missing source/license, compromised source data, excessive telemetry. Document results truthfully.
